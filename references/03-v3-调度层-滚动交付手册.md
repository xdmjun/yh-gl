# 数据流驱动的滚动交付实施手册 v3

> 适用：多模块系统 + 多 AI 窗口并行开发，受 token、限流与人工精力约束。  
> 前置阅读：v2 手册（应化分级、任务包、验证环）。v3 不替代 v2，而是把其中的"任务拆分与派单"替换为数据流驱动版本，并新增滚动批次调度。  
> 版本：3.0。  
> 交付性质：方案与模板；示例取自真实项目实践的抽象，用于演示套用方式。  
> 术语约定：本文术语以项目自建的受控词表（glossary）为准；词表可从最小本体的"实体+别名"节生成。

## 1. 核心变化：从"Spec 拆任务"到"数据流拆任务"

v1/v2 的任务来源是 Spec 状态机：Spec 批准后按能力域拆任务。这在实践中暴露了一个结构性问题：

> **Spec 按功能域组织，但系统按数据架构耦合。** 一个用户故事横跨多个 Spec；一张数据表被多个 Spec 读写；而两个相邻 Spec 的页面可能毫无数据交集。

v3 的解法：

1. **Spec 降级为"规范事实源"**：只回答"每个行为该怎样才算对"，不再直接充当任务清单。
2. **数据架构升为"拆分依据"**：从数据库设计 + API 契约 + 用户故事主线，梳理出谁生产数据、谁消费数据。
3. **任务是数据流的切片**：每个任务绑定"读哪些表/接口、写哪些表/接口、为哪个用户故事服务"，依赖边由数据流向导出。
4. **批次是调度单元**：数据流按用户故事主线切成滚动批次，每批同时跑"本批交付"与"下批预开发"双轨道。

三份文档的新分工：

| 文档 | v2 中的角色 | v3 中的角色 |
|---|---|---|
| Spec | 任务来源 + 验收依据 | **仅验收依据**（accept 指向 Spec 断言不变） |
| 契约（API/DB） | 依赖门（contract_accepted） | **拆分依据**：数据流向图从契约和 DB 设计导出 |
| 任务包 | 切片 + scope + 预算 | 不变，但 `depends_on` 的边由**数据依赖**导出，不再由 Spec 编号顺序导出 |

一句话：**Spec 管"对不对"，数据流管"先后与并行"，v2 的验证环与底线原样保留。**

## 2. 拆分模型：五步从数据架构到任务 DAG

### 2.1 Step 1 — 画数据流向图（人工策展，不靠静态图自动生成）

输入三份资产：数据库设计（表 + 外键 + 写者）、API 契约（端点 + 请求/响应）、用户故事主线（用户操作序列）。

产出一张**数据流矩阵**（每行 = 一张表/一个聚合，每列 = 写者模块 / 读者模块 / 服务的故事）：

| 数据资产 | 写者 | 读者 | 服务的故事 |
|---|---|---|---|
| 主数据 A | 录入 / 同步入口 | 查询与展示模块 | 主线 1 |
| 主数据 B | 录入 / 同步入口 | 查询模块、下游业务模块 | 主线 1、2 |
| 中间态数据 C | 流程驱动方 | 下一环节模块 | 主线 2 |
| 关系 / 映射数据 | 关联维护模块 | 多个消费者模块 | 主线 1~3 |
| 状态 / 凭据类数据 | 状态的权威写方（签发方） | 消费方模块、状态侧展示 | 主线 3 |
| 操作留痕 | 全部模块（旁路写） | 运维 / 合规侧 | 合规 |

> 表中是**形态占位**（A/B/C 代表任意业务实体，非真实表名）。落地时用数据库设计的真实表名替换，并让矩阵行数与真实表/聚合一一对应。

**人工策展是必须的**：静态代码图（CBM）只能确认"代码里谁调用了谁"，推不出"谁被授权写这张表"。数据流向的权威是数据库设计的写者标注 + owner 确认。CBM 在这一步的用途是**波级校验**（见 §2.6：过程中持续比对代码实际调用与矩阵声明，不等联调），不是事前生成矩阵。

**本体挂钩（可选，按 v1 §4.3 应化伸缩）**：已建最小本体的项目，矩阵第一列的数据资产名引用本体实体名，别名与"同一张表两个名字"的裁定以本体为准；无本体项目直接用数据库设计中的表名，流程不塌。矩阵策展时发现本体缺实体或实体与表对不上，记入未知清单提交决议，不静默改任一侧。

### 2.2 Step 2 — 导出依赖边（带类型，沿用 v1 §6 的五类依赖）

数据流向直接映射为依赖边类型：

| 数据关系 | 依赖边类型 | 解锁条件 |
|---|---|---|
| A 写的表，B 要读 | **契约依赖**（B 的接口无关层可先行） | A 的 API 契约 approved |
| A 写的表，B 也要写（或 B 的入参依赖 A 的产出） | **实现依赖**（B 必须等 A 集成） | A implemented + 定向检查通过 |
| 旁路写（不被用户旅程直接消费的支撑数据） | **软依赖**（可并行，集成时补验证） | 各自实现，集成批统一验证 |
| 共享公共文件/环境 | **资源依赖** | 集成角色串行认领 |
| 权限策略变更 | **批准依赖** | owner 签字 |

关键纪律：**契约依赖边的默认并行方式是"接口无关层先行"（组件树、样式、store 骨架、类型、空态/错误态布局），绑定层等真接口就绪后再做；只有预开发产能不足时才降级为 scaffold mock。写者之间若写同一张表，禁止并行。**

**两种"假数据"必须区分**：

| | scaffold mock（等待脚手架） | test fixture（边界态注入） |
|---|---|---|
| 用途 | 接口未 ready，让绑定层先写 | 接口已 ready，注入 403/500/超时/空列表等边界态 |
| 滚动稳态下 | 应趋零（见 §2.4） | 始终需要——真接口无法稳定返回错误态 |
| 生命周期 | 联调切真后删除或降级为单测 fixture | 长期保留在测试代码内 |

### 2.3 Step 3 — 按用户故事主线切批次

用户故事主线（如"进入系统 → 浏览核心对象 → 发起操作 → 走完处置流程 → 结果可查"这类通用五段）切成 4~6 个批次。切批原则：

1. **每批产出一段可演示的用户旅程**（"进入系统后能看到核心对象列表"比"完成 3 个 Spec"更有验收意义）。
2. **批内数据资产尽量不重叠**；重叠的数据资产要么同批、要么用契约依赖隔开。
3. **支撑模块（不被用户旅程直接消费、但被多个下游依赖的）跟它阻塞下游最多的那批走**——被越多下游读的模块，越该在依赖它的第一批交付。
4. **最后一批固定是集成批**（全链路联调 + 回归）。

### 2.4 Step 4 — 批内波次（应化分级插入点）

每批内部不是单一时间线，而是按 v2 的 H1/H2/H3 分级切波次。以最常见的**双端形态**（契约生产方 + 契约消费方，如服务端 ‖ 客户端）为例——单端项目退化为两波：

```
批次 N 内部：
  波次 A（并行）：契约生产方实现（H2）×M 个模块  +  契约消费方接口无关层（H1）×K 个入口
  波次 B（串行）：联调（资源依赖：环境互斥，单线程）+ 绑定层对接真接口 + e2e 场景
  波次 C（预开发，与 A 并行）：下一批的契约依赖任务（生产方接口完整实现 + 消费方接口无关层）
```

波次 C 是滚动交付的引擎：**下一批的生产方接口和消费方接口无关层在本批波次 A 期间就开工**，消耗的是"等待联调"的空闲产能。稳态滚动下，到批次 N+1 时本批接口已 ready，消费方直接对接真接口——**scaffold mock 在常规流程中不出现**。仅两个降级场景允许 mock：① 批次 1 无预开发池，生产方产能落后于消费方；② 预开发窗口被更高优先级任务挤占。这两种情况同时是"滚动系统产能失衡"的信号，应进复盘调整资源，而不是常态化 mock。

**Mock 出现率指标**：每批收口统计"本批有多少入口在开发期使用了等待型 mock"。稳态健康值为 0；>0 需在批次复盘中归因（预开发产能不足 / 契约冻结滞后 / 批次切分倾斜），并调整下批排布。

### 2.5 Step 5 — 批次推进的门禁

每批收口必须满足（沿用 v2 验证报告格式）：

- 批内全部任务的 L1/L2 检查真实通过（退出码为准，`pipefail` 纪律）。
- 至少一个 e2e 用户旅程走通。
- **CBM 波级校验通过**（见 §2.6）：代码实际调用结构与数据流矩阵声明一致；无 CBM 时以表名 grep + 引用检查替代，并在报告中记录降级。
- 接口两侧字段逐字段核对（联调即校验；若本批出现过 scaffold mock，其删除/降级为单测 fixture 必须在门禁前完成）。
- Spec 状态 approved → implemented 更新（**这是 Spec 的唯一写回点**）。
- 各仓（如多仓分立）版本配对登记。

下一批启动条件 = 本批的**实现依赖边**全部满足（不是本批 100% 完成——旁路 bug 登记追踪，不阻塞下一批）。

### 2.6 CBM 波级校验点：过程中验证数据流，不等联调

数据流矩阵是声明，代码实现可能偏离声明。用 CBM 在**每个波次收口**比对代码实际调用结构与矩阵声明，把结构性偏差堵在串行联调之前：

| 偏差类型 | CBM 发现方式 | 最早暴露时点 |
|---|---|---|
| 未声明的读者/写者 | 查询该数据资产相关模块的调用与引用边 | 该模块波次收口 |
| 循环数据依赖悄悄形成 | 调用图环检测 | 波次收口，远早于联调死锁 |
| 预开发接口偏离矩阵 | 比对预开发接口模块的实际读写调用边 | 波次 C 收口 |
| 裸 SQL/动态表名（静态图盲区） | 以表名 grep + 引用检查补充 | 波次收口（兜底手段） |
| 运行时语义/时序错误 | **静态分析不覆盖**——只能靠测试与联调 | 波次 B/集成批 |

**边界必须钉死**：CBM 验证的是"代码结构 ↔ 矩阵声明"的一致性，是门禁的**必要条件而非充分条件**；静态一致通过后，联调与测试照常执行。无 CBM 环境时用表名 grep + 引用检查做同等校验，报告中记录降级，流程不因此失效。

监控指标：**矩阵偏差数**（每波次收口时 CBM 查出的未声明调用/循环/越界数）。持续为 0 说明数据流矩阵与实现保持同步；连续出现偏差说明矩阵过期或模块边界失守，应回到 Step 1 更新矩阵或重划 scope。

### 2.7 契约分层：接口契约之外还有哪些契约

契约 = 两个独立执行单元之间关于共享事物的**冻结的、可校验的约定**，违反它会产生跨单元破坏。接口契约只是最先被识别的成员；环境、技术栈、组件、部署同样满足定义。按"谁消费、变化频率、谁批准"分四层：

| 层级 | 契约类型 | 约定内容 | 变化频率 | 归属位置 |
|---|---|---|---|---|
| L1 系统层 | 技术栈契约 / 环境契约 | 语言与框架版本、包管理器、运行时版本、环境变量清单、端口分配 | 极低（月/季） | **项目规则**（稳定规则区）+ 机器可读事实源（各语言的依赖清单文件 / .env.example） |
| L2 基础设施层 | 组件契约 / 部署契约 | 缓存与存储的键规范/序列化/TTL 归属、schema 与迁移编号分配、目标环境拓扑、进程管理与回滚方式 | 中（随批次演进） | 数据流矩阵扩展列 + 独立部署契约（ADR 系） |
| L3 业务层 | 接口契约 / 数据契约 / 验收契约 | API 请求响应、表写者读者、Spec 断言 | 随批次 | api-contract / database-design / Spec 文档 |
| L4 流程层 | 协作契约 | scope 规则、提交授权、熔断轮次、活跃槽位数 | 低 | 实施手册 + 项目规则 |

**归属判定三问**：① 每个任务都要遵守、几乎不变 → 项目规则；② 随批次演进、被特定任务消费、需版本化 → 契约文档（可作依赖 gate）；③ 一次性事实 → 任务包/ADR。**能用机器可读文件锁定的就不写散文。**

**分层带来的并行收益**：下游任务不必等"所有契约"冻结，只需等它消费的那一层——消费方界面层只需 L3 接口契约 + L1 环境契约（服务地址），生产方预开发只需 L2 组件契约（key 前缀、迁移编号）+ L1 技术栈契约，联调需 L1 环境契约（端口、进程管理）+ L2 部署契约，L4 协作契约对所有窗口常驻。粒度细化直接换来更早解锁。

**批次门禁的契约核对项随之细化**：按任务消费的契约层级核对（如"接口字段核对"扩为"L3 字段 + L1 端口/base URL"）；L2 组件契约新增 key 前缀或迁移编号时，作为依赖 gate 进入波次 C 准入。

**本体的位置**：已建最小本体的项目（v1 §4.3、v2 §7.4），L3 业务契约的实体名与枚举值以本体为对齐源——契约是本体的投影，实体改名或状态机变更时**先改本体（走决议），再改契约**，两侧不一致即"契约冲突"失败路由。L1/L2/L4 与本体无直接依赖，不因本体存在而增加核对项。

#### 2.7.1 通用接入模板（跨项目复用）

上述分层的**结构**通用、**内容**项目特定。新项目接入时按以下模板填空（填空结果写入该项目自己的项目规则文件）；每格必须标注事实源（哪个文件可核实），禁止凭记忆填写。

```markdown
## 系统契约（L1）
### 技术栈版本（以机器可读文件为事实源）
| 项 | 版本 | 事实源 |
| 语言/运行时 |   | 各语言依赖清单（如 go.mod / package.json / requirements.txt / Cargo.toml，按项目技术栈） |
| 框架及关键库 |   | 同上 |
| 包管理器 |   | lockfile（如 pnpm-lock.yaml / go.sum / poetry.lock，按项目技术栈） |
| 构建/检查工具链 |   | 构建配置文件 |

### 环境约束
| 项 | 值 | 说明 |
| 运行参数（host/绑定地址等易错默认值） |   | 本地实测，勿照搬框架文档 |
| 配置文件位置与秘密边界 |   | 哪些入库、哪些 gitignore |
| 环境变量清单 |   | .env.example |

### 端口/资源分配
| 端口/资源 | 用途 |
| （按服务逐行列） |   |

### L1 变更规则
变更需 owner 批准：改本节 + 对应事实源 + 变更日志。AI 窗口不得为绕过失败擅自修改以上值。
```

**按项目形态裁剪**（避免小项目填空表格）：

| 项目形态 | 裁剪 |
|---|---|
| 纯客户端 / 纯脚本 | 删"端口分配"；L2 部署契约可暂缓 |
| monorepo | 增加"包间契约"（workspace 依赖方向、共享包版本策略） |
| 嵌入式/跨端 | L1 换成交叉工具链、目标硬件约束 |
| 无外部组件 | L2 只留部署契约；数据流矩阵组件列可空 |
| 单人单窗口 | L4 简化为"提交授权 + 验证纪律"两条 |

L2~L4 不提供填空模板：它们随批次演进产生，首次出现即写入对应文档（组件契约进矩阵扩展列、部署进 ADR、协作进手册），不要在启动时预先虚构。

## 3. 与多 Agent / 多窗口的结合

### 3.1 窗口角色与批次的关系

v2 的三种角色（统筹/实现/验证）在 v3 中映射到批次轨道：

| 窗口 | 批次内的岗位 | 波次切换 |
|---|---|---|
| 统筹窗口 | 维护批次看板、派单、认领公共资源、联调收口 | 全程在场，是单写者 |
| 生产方窗口 ×N | 当前批模块实现 + 下批骨架（预开发） | 波次 A→C 无缝切换 |
| 消费方窗口 ×N | 当前批接口无关层 → 联调绑定真接口 → 下批接口无关层 | 波次 A→B→C |
| 验证窗口 | 按需激活（H3 任务、批次门禁复核） | 波次 B 前激活，完成后释放槽位 |

**同一窗口跨批次复用**是 v3 的效率来源：消费方窗口切完本批接口无关层，联调等待期直接开始下批的接口无关层，不需要重新派单建上下文——任务包用 `profile` 字段标记属于哪个波次。

### 3.2 并行度约束

- **实现类任务**：并行数 = scope 不重叠的模块数（数据流矩阵保证写者互斥）。
- **联调**：全局单线程（环境互斥：DB、端口、外部服务）。
- **预开发**：与实现并行，但吃同一配额池——额度紧张时按 v2 §5.1 的 B 信号降并行，预开发让位于本批交付。
- 波次间同步点 = git commit + 批次看板更新（廉价同步，不共享实时上下文）。

### 3.3 应化分级在 v3 中的落点

| 分级信号 | 批次层面的含义 |
|---|---|
| 风险 R | 触碰安全边界 / 数据迁移 / 外部通道的批次，波次 B 加独立验证窗口（H3） |
| 不确定性 U | 契约未冻结的模块不许进波次 C 预开发（防 mock 漂移） |
| 耦合 C | 数据流矩阵中读写者 ≥3 的表，其模块串行处理 |
| 资源 B | 联调窗口是稀缺资源，预开发不占用联调环境 |

## 4. 五个已知风险与 v3 的护栏

| 风险 | 表现 | v3 护栏 |
|---|---|---|
| 数据依赖 ≠ 全部依赖 | 视觉一致性、公共组件、入口/条件展示逻辑不在数据流上 | 数据流矩阵加一列"共享资产"；公共组件进资源依赖，由集成角色统一改 |
| Mock 漂移 | 契约中途变更，消费方 mock 与生产方实现脱节，联调才暴露 | 波次 C 只做"契约已冻结"的预开发；联调切真时逐字段核对契约；漂移即修 mock 不修生产方 |
| 静态图推不出业务依赖 | 用 CBM 自动生成批次会漏掉写者授权关系 | 数据流矩阵人工策展 + owner 确认；CBM 仅做事后调用一致性校验 |
| 批次倾斜 | 按数据流切批天然不均匀（某批 4 模块，某批 1 模块） | 大批内部再切波次并行；小批与大批相邻时合并窗口资源 |
| 联调串行瓶颈 | 多批挤同一个联调窗口 | 联调环境互斥单线程；预开发保证联调等待期不停产；注意运行环境的进程生命周期管理（如 Windows 的进程树随会话回收），服务启动→探测→清理应在单次会话内完成 |

## 5. 首批启动清单（通用）

- [ ] 数据流矩阵初稿（表 × 写者/读者/故事），owner 确认
- [ ] 用户故事主线切 4~6 批，标注每批触发条件（依赖边类型）
- [ ] 批次 1 的任务包（含 `profile` 波次标记 + 数据依赖 gate）
- [ ] 波次 C 预开发候选清单（仅含契约已冻结的模块）
- [ ] 联调环境认领规则（单线程，登记占用）
- [ ] 批次门禁 checklist 嵌入验证报告模板
